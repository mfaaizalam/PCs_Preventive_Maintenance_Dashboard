1. What This Document Covers
Before writing any production code, this document lays out how the system will be structured and why, so the whole team is working from the same plan. It covers the new clean folder structure, the PostgreSQL (Neon) database design, the migration strategy, how the existing Excel preventive-maintenance list fits into the system, the baseline UI direction carried over from the prototype, and how the work can be split across three teams (Frontend, Backend, Agent).
Ground rules confirmed from our discussion, so they're written down and not lost:
Deployment stays local — the backend and dashboard run on a PC/small server inside the department. There is no plan to publicly host or deploy this to the internet.
Only the database moves to the cloud — Neon (serverless Postgres) — so 2–3 machines' data stays centrally available, backed up, and reachable without maintaining a local Postgres server.
Storage stays lean by design — with only a handful of PCs reporting every ~30 seconds, we will not log every single reading forever. The schema below is built around “update the current state, log history only when something meaningful happens.”
The Excel master list is preserved as data, not thrown away — it becomes the seed data and ongoing checklist module inside the system, not a separate to-do file.
Alembic is recommended for database version control (see Section 4) — you asked me to evaluate it and include it if it's a good fit; it is, and it's the standard companion to the SQLAlchemy setup already used in the prototype.

3. Database Design — PostgreSQL on Neon
3.1 Core Design Principle: Live State vs. History
The prototype already uses a good pattern worth keeping: one row per computer that is UPDATED (not inserted) on every check-in, so the “current status” table never grows. We extend that same idea to the new hardware and license data, and we deliberately do NOT create a new row every 30 seconds for everything — that's what was driving the “millions of rows” concern.
computers — one row per PC, upserted on every agent report. Always current, always small (one row per lab machine).
Detail tables (ram_slots, storage_devices, peripherals, software_licenses) — also upserted per PC. A RAM slot's row is only replaced when its contents actually change, not every heartbeat.
metrics_history — the only table that grows over time, and it's written on a coarser interval (e.g. one point every 5 minutes, or on threshold breach) rather than every 30-second heartbeat, plus a retention job that drops rows older than N days.
hardware_change_log / alerts — append-only, but only written when something actually changes or crosses a threshold — not on a timer.
Rough volume check for peace of mind: even storing every 30-second reading for 3 PCs would be about 8,600 rows/day — nowhere near “millions,” and Neon's free/low tier handles that easily. But the pattern above keeps it smaller still and keeps queries fast as the lab count grows later.

4. Migrations — Alembic (Recommended)
You asked for my view on using Alembic for database version control — yes, it's the right call here, for a simple reason: the backend already uses SQLAlchemy, and Alembic is its official migration companion. It lets the team change the schema (add a column, add a table) as a tracked, reviewable, reversible script instead of hand-editing the Neon database.
Every schema change becomes a numbered, committed file in alembic/versions/ — visible in Git, reviewable like code.
The same migration applies cleanly to a developer's local Postgres and to the shared Neon database — no “works on my machine” schema drift.
Changes can be rolled back (alembic downgrade) if a change turns out to be wrong.

5. Neon Cloud + Local Deployment — How It Fits Together
Backend (FastAPI) and Dashboard (React) run locally inside the department — on the IT Manager's PC or a small always-on machine on the local network. No public hosting is planned.
Only DATABASE_URL in backend/.env points to Neon — the backend talks to Neon over the internet for storage, but the app itself is only reachable on the local network.
Agents on each lab PC call the local backend's IP (e.g. http://192.168.x.x:8000), same as the prototype does with --server.
Benefit: no local Postgres server to install/back up/maintain, automatic backups on Neon's side, and the data is durable even if the local backend PC is reformatted.
